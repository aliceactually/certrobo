# CertRobo PR #15 review — 2 November 2026

Reviewed PR head `399dced189d3a1721396f936d35fcef2ed42e00b` against `master` `c7ee28907fa86d173d7d97d9f0474b42a47ce139`. Recommendation: hold the merge while the following lifecycle failures are addressed.

## Findings

1. **Equivalent serial encodings create a permanent unpublished-revocation loop.** `SeedRevokedSerialAsync` (`CertificateAuthorityService.cs:2276-2326`) compares the normalized *text* rather than the numeric serial, so `03E9` and `0003E9` are treated as different certificate records despite representing the same X.509 serial number. `GenerateAndPersistCrlInternalAsync` emits both as the same integer (`:3039-3050`); `IsCertificateRevocationUnpublished` (`:2748-2789`) retrieves only one matching CRL entry. With different revocation reasons/timestamps, one record remains pending indefinitely. In an isolated Linux test I issued and revoked a certificate, then seeded its serial prefixed with `00` and a different reason. Seeding reported publication success, but one record remained pending; two consecutive refreshes published additional CRLs and the record remained pending each time. Normalize and compare serials by canonical positive integer per issuer, prevent ambiguous duplicate CRL entries, and handle already-existing duplicates explicitly. Test sign-padding, leading zeros, and already-existing data; retries must converge and expose any genuine conflict.

2. **A failed database write for one issuer contaminates refresh of another.** `RefreshDueCrlsAsync` (`:2503,2546-2625`) reuses one tracked EF context for all issuers. If `GenerateAndPersistCrlInternalAsync` adds a CRL and updates its authority (`:3082-3096`), then `SaveChangesAsync` fails, the catch reports the error but leaves the failed tracked changes in the context. The next issuer's save retries the first issuer's failed insertion as well. In an isolated Linux test with two issuers and pending revocations, an SQLite trigger simulated an issuer-specific insert failure for issuer A. A's refresh failed as expected, but issuer B's refresh also failed and its previous CRL remained current. Removing the trigger let a new refresh publish both. Isolate each issuer's publication in its own clean context/transaction, or reliably discard all failed tracked changes before continuing. Add a failure injected at the actual persistence step, not only before CRL generation, and prove B can advance while A remains pending.

3. **New pending work can wait almost 30 minutes before the first retry.** `CrlRefreshBackgroundService.cs:11-12,18-58` chooses a 30-minute sleep after a clean scan and switches to one-minute retries only after a later scan has already found an error. A revocation recorded while the signer is locked, immediately after the clean scan, does not wake the sleeping service; unlocking does not wake it either. Thus the first automatic retry can be nearly 30 minutes later despite the intended prompt retry. Signal pending work/unlock or use a bounded frequent scan, and test a revocation arriving *after* a clean scan with a controllable clock or wake mechanism. This finding is source-supported; no 30-minute live timing test was run. Manual refresh still works.
